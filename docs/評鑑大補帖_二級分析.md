# 第 0 章：Pipeline 總覽

## 0.1 這條 pipeline 在做什麼

**二級分析（Secondary Analysis）** 的定義：從定序儀出來的原始 reads，
產生「這個人有哪些變異」的清單。**不做臨床判讀**（那是三級分析的事）。

```
定序儀 FASTQ
    │
    ├─ 01 前處理     fastp        去 adapter、去低品質 read
    │
    ├─ 02 對位       Parabricks   bwa-mem 對到 hg38 → 標記重複 → BQSR
    │                fq2bam       （GPU 加速，一步到位出 BAM + recal table）
    │
    ├─ 03 對位 QC    samtools stats / mosdepth / ploidy_check
    │
    ├─ 04 SNV/indel  DeepVariant（GPU）＋ HaplotypeCaller（GPU）→ VQSR
    │                → （選用）WhatsHap phasing + compound 合成
    │                → bcftools ensemble 合併兩個 caller
    │
    ├─ 05 CNV/SV     WGS: CNVkit + Delly    WES: gCNV + CNVkit + Delly
    │                （Manta 選用，非商用授權）
    │
    ├─ 06 STR        GangSTR（依染色體平行）
    │                （ExpansionHunter 選用，非商用授權）
    │
    ├─ 07 粒線體     Broad mtDNA best practice（正常 + 位移參考雙路 Mutect2）
    │
    └─ 08 ROH        bcftools roh（選用）／ AutoMap（選用，非商用授權）
                            ↓
                     MultiQC 匯總報告
```

## 0.2 三個貫穿全 pipeline 的設計原則

### 原則一：商業授權是硬約束

**每一個「預設會跑」的工具，都必須可商業使用。**
非商用授權的工具一律做成 flag，**預設 OFF**。

| 工具 | 授權 | 可商用 | 預設 |
|------|------|--------|------|
| fastp | MIT | ✅ | 預設路徑 |
| Parabricks | NVIDIA EULA（機構授權） | ✅ | 預設路徑 |
| GATK | BSD-3 / Apache-2.0 | ✅ | 預設路徑 |
| DeepVariant | BSD-3 | ✅ | 預設路徑 |
| samtools / bcftools | MIT | ✅ | 預設路徑 |
| mosdepth | MIT | ✅ | 預設路徑 |
| CNVkit | Apache-2.0 | ✅ | 預設路徑 |
| Delly | BSD-3 | ✅ | 預設路徑 |
| GangSTR | GPL-3.0 | ✅ | 預設路徑 |
| bcftools roh | MIT/GPL | ✅ | `--run_roh`（本院預設開） |
| **Manta** | PolyForm Strict 1.0.0 | ❌ 僅非商用 | `--run_manta`，**OFF** |
| **ExpansionHunter** | PolyForm Strict 1.0.0 | ❌ 僅非商用 | `--run_expansionhunter`，**OFF** |
| **AutoMap** | 無公開授權 | ❌ 不明 | `--run_automap`，**OFF** |

> **評鑑要點**：如果被問「你們用的軟體有沒有授權問題？」
> 答案是：預設臨床路徑**完全沒有**非商用工具，
> 三個非商用工具都在 flag 後面且預設關閉，且 README 有完整授權表。

### 原則二：對齊 Broad Institute 已發表的最佳實踐

2026-07 第一次評鑑後，科部提出兩個問題：

1. **Delly 吐出太多 SV** → 只發布 `FILTER=PASS`
   （`delly filter -f germline` 需要 ≥10 個樣本比較深度比值，單樣本不能用，
   所以 PASS 過濾是單樣本情境下唯一正確的做法）
2. **CNV 相對其他平台漏掉** → 診斷後發現漏掉的事件在 CNVkit 原始 `.cns` 裡就不存在
   （不是被 `--filter cn` 濾掉），但 **Delly PASS 抓得到** → 那些是 SV 型事件，
   深度法的 CNVkit 天生看不到。**決定：停止 ad-hoc 調參，全面對齊 Broad 官方預設值。**

對齊清單見第 8 章與第 14 章。

### 原則三：GPU 資源要能共享

DGX-2 上有 6 張 V100，二級與三級分析共用。
所以有 `gpu_lock.sh` / `gpu_unlock.sh`：process 開始時**原子性地搶一張卡**，
結束時（含失敗、被 kill）用 `trap ... EXIT` **一定歸還**。
見第 15 章。

## 0.3 為什麼用 Nextflow DSL2 sub-workflow

`main.nf` 現在是**純組合**（pure composition）——它只負責把 sub-workflow 串起來，
不含任何 `process`。每一個分析領域（SNV、CNV、STR、mito、ROH）
各自是一個 sub-workflow，把「這個領域要跑哪些工具、flag 怎麼判斷」
全部收在自己的 module 檔案內。

**好處**：
- `main.nf` 一眼看完（176 行，其中一半是授權宣告）
- 要改 CNV 的邏輯，只需要動 `modules/cnv_sv.nf`，不用碰 `main.nf`
- flag 判斷（`--run_manta` 等）收在 sub-workflow 內部，`main.nf` 不需要知道

**代價**：
- 空 channel 的 sub-workflow 會產生 0 個 task，在 DAG 上顯示為 `-`
  （這是正常的，不是錯誤 —— 例如 WGS 時 gCNV 不跑）

```groovy
// 啟用 Nextflow DSL2 語法（才能用 workflow / include / sub-workflow）
nextflow.enable.dsl = 2

// ---------------------------------------------------------------------------
// 【include 區】把各 module 的 sub-workflow / process 引進來
//
// 命名慣例：
//   - 全大寫 + 底線     = process 或 sub-workflow
//   - CALL_xxx          = 該領域的 sub-workflow（內含多個 process + flag 判斷）
//   - 其他（FASTP 等）  = 單一 process
//
// 注意 FASTP、PARABRICKS_FQ2BAM、MULTIQC 是「單一 process」直接 include，
// 因為它們沒有分支邏輯，包成 sub-workflow 只是多一層無意義的包裝。
// ---------------------------------------------------------------------------
include { FASTP }                           from './modules/preprocessing'   // 去 adapter / 去低品質
include { PARABRICKS_FQ2BAM }               from './modules/alignment'       // GPU 對位 + markdup + BQSR
include { ALIGNMENT_QC }                    from './modules/alignment_qc'    // stats + mosdepth + ploidy
include { CALL_SNV }                        from './modules/call_snv'        // DV + HC + VQSR + ensemble
include { CALL_CNV_SV }                     from './modules/cnv_sv'          // CNVkit / gCNV / Delly / Manta
include { CALL_STR }                        from './modules/repeat'          // GangSTR / ExpansionHunter
include { CALL_MITO }                       from './modules/call_mito'       // Broad mtDNA best practice
include { MULTIQC }                         from './modules/postprocessing'  // QC 匯總
include { CALL_ROH }                        from './modules/roh'             // bcftools roh / AutoMap

// ---------------------------------------------------------------------------
// 【前置檢查】沒給 samplesheet 就直接失敗，不要跑到一半才炸
// 用中文錯誤訊息，因為使用者是本院同仁
// ---------------------------------------------------------------------------
if (!params.input_csv) {
    error "錯誤：請提供 --input_csv 參數"
}

workflow {

    // =========================================================
    // (A) 讀取 Samplesheet
    // 格式：sample,fastq_1,fastq_2,sex
    // sex 填 male / female / unknown
    //
    // 【設計說明】為什麼要有 meta map？
    //   Nextflow 的 channel 元素慣例是 [meta, files]，meta 是一個 map，
    //   一路帶著樣本的中繼資料（id / 性別 / lane），這樣任何一個 process
    //   都能拿到「這是誰、什麼性別」，不需要額外的 channel 去 join。
    //
    // 【為什麼需要 sex？】
    //   - bcftools +fixploidy 要靠性別決定 chrX/chrY 的倍體（男性非 PAR 區為單套）
    //   - gCNV 的 contig ploidy prior 要靠性別
    //   - 倍體 QC（ploidy_check.py）要拿實際深度去對照宣告的性別
    //
    // 【為什麼 lane 是選填？】
    //   多數樣本一個 lane 跑完；但有些樣本會跨 lane。有 lane 欄位時，
    //   同一個 sample 的多個 lane 會在 (C) 被 groupTuple 合併成一個 BAM，
    //   並在 alignment.nf 組出正確的 @RG read group 字串。
    // =========================================================
    ch_input = Channel
        .fromPath(params.input_csv)      // 讀 CSV 檔
        .splitCsv(header: true)          // 以第一列為欄位名切成 map，每列一個元素
        .map { row ->
            def lane  = row.lane ?: 'L001'  // 沒有 lane 欄位就預設 L001
            def meta  = [
                // id：這一筆 channel 元素的唯一鍵。有 lane 時要帶 lane，
                //     否則同一 sample 的兩個 lane 會被 Nextflow 視為同一鍵而衝突。
                id:        row.lane ? "${row.sample}_${lane}" : row.sample,
                sample_id: row.sample,               // 真實 sample ID（FQ2BAM 用）
                sex:       row.sex ?: 'unknown',     // 沒填就 unknown（倍體修正會跳過）
                lane:      lane
            ]
            def reads = [file(row.fastq_1), file(row.fastq_2)]  // file() 把字串轉成 Nextflow 檔案物件
            return [meta, reads]
        }

    // =========================================================
    // (B) Step 1: Preprocessing
    // fastp：去 adapter、去低品質尾端、丟掉太短的 read
    // 詳見第 3 章
    // =========================================================
    FASTP(ch_input)

    // =========================================================
    // (C) Step 2: Alignment + BQSR
    //
    // 【為什麼參考序列要一個一個 file() 傳進去？】
    //   Apptainer 容器內看不到主機的任意路徑。Nextflow 只會把「宣告成 input 的檔案」
    //   symlink 進 work 目錄並綁進容器。所以 bwa 索引的 5 個副檔名
    //   (.amb/.ann/.bwt/.pac/.sa) 和所有 known-sites VCF 的 .tbi 都得明列，
    //   少一個就會在容器裡 file not found。
    // =========================================================
    ch_fasta      = file(params.fasta)                              // hg38 主序列
    ch_fasta_fai  = file("${params.fasta}.fai")                     // samtools faidx 索引
    ch_fasta_dict = file(params.fasta.replace('.fasta', '.dict'))   // GATK 需要的 sequence dictionary

    // 把 FASTP 出來的 channel 重整成 fq2bam 要的形狀：
    //   輸入 [meta(含 lane), [R1, R2]]  →  輸出 [meta(含 lanes list), [R1a,R2a,R1b,R2b,...]]
    ch_fq2bam_input = FASTP.out.reads
        .map { meta, reads ->
            // 把 meta.id 換回 sample_id，保留 sex 和 lane
            // lane 資訊保留在 lanes list，供 alignment.nf 組 RG 字串用
            //
            // 【關鍵】把 id 從 "SAMPLE_L001" 換回 "SAMPLE"，
            //   groupTuple 才會用 sample 當鍵，把同一樣本的多 lane 收在一起。
            def new_meta = [id: meta.sample_id, sex: meta.sex]
            [new_meta, meta.lane, reads]
        }
        .groupTuple()   // 同一 sample_id 的所有 lane reads 合併成 list
                        // → [meta, [L001, L002], [[R1a,R2a], [R1b,R2b]]]
        .map { meta, lanes_list, reads_list ->
            // 按 lane 排序，確保 lanes 和 reads 順序一致
            //
            // 【為什麼一定要排序？】groupTuple 不保證順序（誰先跑完誰先進）。
            //   若 lanes list 與 reads list 順序不一致，@RG 會貼錯 lane，
            //   BQSR 的 per-lane 誤差模型就會學錯 → 結果不可重現。
            //   transpose() 把兩個 list 併成 pair，一起排序後再拆開，保證對齊。
            def sorted = [lanes_list, reads_list].transpose()   // [[L001,[R1a,R2a]], [L002,[R1b,R2b]]]
                .sort { a, b -> a[0] <=> b[0] }                 // 依 lane 名稱字典序排
            def sorted_lanes = sorted.collect { it[0] }                  // [L001, L002]
            def sorted_reads = sorted.collect { it[1] }.flatten()        // [R1a,R2a,R1b,R2b]
            def new_meta = meta + [lanes: sorted_lanes] // 把 lanes 存進 meta，reads 展平
            [new_meta, sorted_reads]   // [[R1a,R2a],[R1b,R2b]] → [R1a,R2a,R1b,R2b]
        }

    // Parabricks fq2bam：bwa-mem 對位 → coordinate sort → MarkDuplicates → BQSR table
    //   一個 GPU process 做完 GATK 最佳實踐前四步，30x WGS 約 40 分鐘（6 張 V100）
    PARABRICKS_FQ2BAM(
        ch_fq2bam_input,
        ch_fasta,
        ch_fasta_fai,
        ch_fasta_dict,
        // --- bwa index 的五個檔案，缺一不可 ---
        file("${params.fasta}.amb"),   // bwa: 模糊鹼基（N）位置
        file("${params.fasta}.ann"),   // bwa: 序列名稱與長度註記
        file("${params.fasta}.bwt"),   // bwa: Burrows-Wheeler 轉換表（最大的檔）
        file("${params.fasta}.pac"),   // bwa: 2-bit 壓縮的參考序列
        file("${params.fasta}.sa"),    // bwa: suffix array
        // --- BQSR 的 known sites，每個都要配 .tbi 索引 ---
        //     BQSR 的原理：把「不在已知變異位點」的 mismatch 當成定序錯誤，
        //     用來建誤差模型。所以 known sites 給得越完整，模型越準。
        file(params.dbsnp),        file("${params.dbsnp}.tbi"),         // dbSNP 138
        file(params.known_indels), file("${params.known_indels}.tbi"),  // Mills gold standard indels
        file(params.known_indels2),file("${params.known_indels2}.tbi"), // GATK known indels
        file(params.known_snps),   file("${params.known_snps}.tbi")     // 1000G phase1 high-conf SNPs
    )
    // alignment_bundle = [meta, bam, bai, recal_table]
    //   打包成一個 tuple，讓下游任何要 BAM 的 process 都能直接 join
    ch_bam = PARABRICKS_FQ2BAM.out.alignment_bundle

    // =========================================================
    // (D) Step 3: Alignment QC（sub-workflow：SAMTOOLS_STATS + MOSDEPTH + PLOIDY_CHECK）
    //
    // 【為什麼 QC 統一走 mosdepth？】
    //   早期 WES 的倍體判斷是拿 gCNV 的 contig-ploidy 結果，WGS 走 mosdepth，
    //   兩條路徑輸出格式不同、不好比較。現在統一：不分 WES/WGS 都用 mosdepth
    //   算 per-contig 平均深度，再由 ploidy_check.py 判性別。
    //   gCNV 的 ploidy 仍然存在（那是 gCNV 內部必要步驟），但 QC 報告只看 mosdepth。
    // =========================================================
    ALIGNMENT_QC(ch_bam)
    // (meta, summary.txt)：MultiQC 用；PLOIDY_CHECK 在 sub-workflow 內部已消費同一輸出
    ch_mosdepth_summary = ALIGNMENT_QC.out.summary

    // =========================================================
    // (E) Step 4-5: SNV/indel calling + ensemble（sub-workflow）
    //   內含 DeepVariant / HaplotypeCaller / VQSR（各為第二層 sub-workflow）、
    //   PHASE_COMBINE（--run_phasing）、BCFTOOLS_ENSEMBLE、DV/ensemble stats。
    //
    // 【為什麼跑兩個 caller？】
    //   DeepVariant（CNN）與 HaplotypeCaller（haplotype 重組 + 貝氏）的錯誤模式不同。
    //   兩者都叫到的變異可信度極高；只有一個叫到的，三級分析會標記 caller 來源，
    //   由判讀者決定是否採信。ensemble VCF 的 FORMAT 保留兩個 caller 各自的 AD/DP。
    // =========================================================
    CALL_SNV(ch_bam)

    // Lane 3: CNV / SV（CNVkit(WGS) + Delly + Manta(選) + gCNV(WES)）；CNVkit 用 DeepVariant VCF
    //
    // 【為什麼 CNVkit 要吃 DeepVariant VCF？】
    //   CNVkit 用雜合位點的 B-allele frequency 來判斷等位基因不平衡（allelic imbalance），
    //   可以區分「真的 copy number 改變」與「單純深度波動」，也能抓 copy-neutral LOH。
    //   給的是 DV 的 VCF（不是 ensemble），因為這一步在 ensemble 完成前就能開跑。
    CALL_CNV_SV(ch_bam, CALL_SNV.out.dv_vcf)

    // Lane 4: STR（GangSTR 依染色體平行化 → 合併；選用 ExpansionHunter）
    CALL_STR(ch_bam)

    // Lane 5: Mitochondria variant calling
    CALL_MITO(ch_bam)

    // Lane 6: ROH（sub-workflow：bcftools roh + AutoMap，皆選用、預設關閉；ROH 不納入評鑑）
    //   用 HaplotypeCaller raw VCF（保留 GT/AD）；flag 收在 CALL_ROH 內部。
    //
    // 【為什麼 ROH 用 HC raw 而不是 ensemble？】
    //   bcftools roh 需要連續、密集的基因型與 AD 來跑 HMM。
    //   ensemble 經過 merge 後某些位點的 FORMAT 會來自不同 caller，密度也被過濾稀釋；
    //   HC raw VCF 是單一 caller 的完整輸出，GT/AD 一致，最適合 HMM。
    CALL_ROH(CALL_SNV.out.hc_vcf_raw)

    // =========================================================
    // (F) MultiQC 匯總
    //
    // 【設計說明】用 Channel.empty().mix(...) 而不是 concat：
    //   mix 不在意上游 channel 何時就緒、也允許某些 channel 是空的
    //   （例如 WGS 沒有 gCNV），空的就自然不貢獻檔案。
    //   最後 .collect() 把全部檔案收成「一個」list → MultiQC 只跑一次。
    // =========================================================
    ch_multiqc = Channel.empty()
        .mix(FASTP.out.json)                             // fastp 的 read 過濾統計
        .mix(PARABRICKS_FQ2BAM.out.qc_metrics)           // duplicate metrics
        .mix(ALIGNMENT_QC.out.stats)                     // samtools stats
        .mix(ALIGNMENT_QC.out.global_dist)               // mosdepth 全基因體深度分佈
        .mix(ch_mosdepth_summary.map { meta, f -> f })   // mosdepth summary（去掉 meta 只留檔案）
        .mix(CALL_SNV.out.dv_stats)                      // DeepVariant bcftools stats
        .mix(CALL_SNV.out.ensemble_stats)                // ensemble bcftools stats
        .collect()

    MULTIQC(ch_multiqc)
}
```

# 第 2 章：`nextflow_main.config` — 執行環境與參數

## 2.1 這個檔案的三大區塊

```
profiles { ... }    ← 四個執行環境（local / dgm / dgx / dgx_single）
params { ... }      ← 全域參數預設值
process { ... }     ← 每個 process 用哪個容器、要多少 CPU/RAM
```

## 2.2 ⚠️ 最重要的坑：`params` 區塊在 `profiles` 後面

Nextflow 讀 config 是**由上往下依序賦值，後面的覆蓋前面的**。
本檔案的 `profiles {}` 在**前**、全域 `params {}` 在**後**，所以：

> **任何在全域 `params {}` 裡宣告的參數，都會蓋掉 profile 裡設的值。**

因此凡是「每個環境要不同值」的參數（例如 `use_gpu_lock`、`ref_dir`、`gpu_ids`），
**只能寫在 profile 裡，絕對不能同時在全域 `params {}` 再宣告一次**。
（三級分析的 config 也踩過同一個坑，見三級大補帖。）

```groovy
process {

    //   104 = 連線被重置
    //   134 = SIGABRT
    //   139 = SIGSEGV

    errorStrategy = { task.exitStatus in [143,137,104,134,139] ? 'retry' : 'finish' }

    withName: 'WHATSHAP_PHASE'  { container = "${params.sif_dir}/whatshap_2.8.sif";   cpus = 1; memory = { task.attempt > 1 ? 8.GB : 4.GB } }
```

## 2.4 評鑑常見問題速查

| 問題 | 在哪裡看 | 答案 |
|------|----------|------|
| 「你們用哪一版 GATK？」 | `withName: 'GATK.*'` | `gatk_4.6.2.0.sif` |
| 「軟體版本怎麼固定？」 | 全部 `withName` 區塊 | 每個工具綁定一個帶版本號的 `.sif`，不從網路拉 latest |
| 「跑失敗會怎樣？」 | `errorStrategy` | 只有 OOM/被砍等 5 種 exit code 會重試 2 次；其他錯誤直接停 |

| 「換一台機器要改幾個地方？」 | `profiles` | 一個 profile 區塊；`ref_dir` 改了，PON/參考檔路徑全部自動跟著換 |

# 第 3 章：`modules/preprocessing.nf` — 前處理（fastp）

## 3.1 這一步在做什麼、為什麼要做

定序儀吐出的 FASTQ 有三類雜訊必須先清掉，否則會污染後面所有步驟：

1. **Adapter 序列** — 當 DNA 片段比 read 長度短時，定序會讀穿片段、讀到接頭序列。
   這段序列不屬於樣本，硬對到基因體上會產生假的 soft-clip 和假的變異。
2. **低品質尾端** — Illumina 定序後段品質會下降，末端幾個鹼基常常是錯的。
3. **過短的 read** — 太短的 read 對位不專一（multi-mapping），只會製造雜訊。

**為什麼選 fastp？** 一次讀檔就同時做完 QC 統計 + adapter 偵測 + 品質修剪 + 過濾，
比傳統的 FastQC + Trimmomatic 兩階段快很多，而且輸出 JSON 可直接餵 MultiQC。
授權 MIT，可商用。

```groovy
/*
 * =========================================================
 * WGS/WES Germline Analysis Pipeline - Preprocessing Module
 * =========================================================
 * Author   : Po-Yu Lin (林伯昱)
 * Institute: Department of Neurology and
 *            Department of Genomic Medicine,
 *            National Cheng Kung University Hospital
 * Contact  : p88124019@gs.ncku.edu.tw

 * Copyright (c) 2026, Po-Yu Lin (林伯昱)
 *  （GPL-3.0-or-later 全文與 main.nf 相同；第三方授權宣告中提到的
 *    main_research.nf 已退役，選用工具現在是 main.nf 的 flag）
 * =========================================================
 */

process FASTP {
    // tag：Nextflow 執行時顯示在 process 名稱後面的標籤，用來分辨是哪個樣本
    //      例如 log 會顯示 [FASTP (NA12878)]
    tag "$meta.id"
    // 實測：RAM 6.4GB，CPU 740%（~8 cores）
    // withName 在 config 有個別設定，label 作為 fallback
    label 'process_medium'

    // publishDir：把 output 宣告的檔案複製到最終輸出目錄
    //   mode: 'copy'  → 實體複製（預設是 symlink，但 work 目錄清掉後 symlink 會斷）
    //   路徑用 `meta.sample_id ?: meta.id`：有多 lane 時 meta.id 帶 lane 後綴，
    //   但輸出要收在「樣本」資料夾下，所以優先用 sample_id。
    publishDir "${params.out_dir}/${meta.sample_id ?: meta.id}/01_preprocessing", mode: 'copy'

    // INPUT:
    //   meta  - sample metadata map（id, sex）
    //   reads - [R1.fastq.gz, R2.fastq.gz] paired-end reads
    input:
    tuple val(meta), path(reads)

    // OUTPUT:
    //   reads - adapter-trimmed, quality-filtered FASTQ pair
    //   json  - fastp QC metrics（供 MultiQC 使用）
    //   html  - fastp QC HTML report
    output:
    tuple val(meta), path("*.fastp.fastq.gz"), emit: reads   // 帶 meta 往下傳給對位
    path "*.json",                             emit: json    // 不需要 meta，直接餵 MultiQC
    path "*.html",                             emit: html    // 人看的報告

    script:
    def prefix = "${meta.id}"
    """
    fastp \
        --in1 ${reads[0]} \                      # R1 輸入
        --in2 ${reads[1]} \                      # R2 輸入
        --out1 ${prefix}_1.fastp.fastq.gz \      # R1 輸出（自動 gzip）
        --out2 ${prefix}_2.fastp.fastq.gz \      # R2 輸出
        --json ${prefix}.fastp.json \            # 機器可讀的統計 → MultiQC
        --html ${prefix}.fastp.html \            # 人可讀的互動報告
        --report_title "${prefix}_fastp_report" \  # HTML 報告標題帶樣本名，方便辨識
        --thread ${task.cpus} \                  # 執行緒數；用 task.cpus 讓 config 統一管理

        # ---- Adapter 處理 ----
        --detect_adapter_for_pe \                # 【重要】自動偵測 PE adapter 序列。
                                                 #   不必手動指定 adapter，fastp 會用 read 重疊
                                                 #   區推算真正的接頭序列 → 換套組也不用改參數。

        # ---- 錯誤校正 ----
        --correction \                           # PE overlap 校正：R1/R2 重疊區若不一致，
                                                 #   用品質分數高的那個覆蓋低的。可降低定序錯誤。

        # ---- QC 分析 ----
        --overrepresentation_analysis \          # 統計過度出現的序列（污染、殘留 adapter 的線索）

        # ---- 滑動窗品質修剪 ----
        --cut_front \                            # 從 5' 端開始滑動窗，品質不足就切掉
        --cut_tail \                             # 從 3' 端開始滑動窗，品質不足就切掉
        --cut_mean_quality 20 \                  # 滑動窗平均品質門檻 Q20（= 1% 錯誤率）
                                                 #   【為什麼是 20？】見 3.3 的「品質分箱」說明

        # ---- 長度過濾 ----
        --length_required 50 \                   # 修剪後短於 50 bp 就丟棄。
                                                 #   50 bp 是 bwa-mem 對 hg38 能維持專一性的下限。

        # ---- 整條 read 的品質過濾 ----
        --qualified_quality_phred 15 \           # 定義「合格鹼基」= Q15 以上
        --unqualified_percent_limit 40           # 一條 read 中不合格鹼基超過 40% 就整條丟棄
    """
}
```

## 3.3 ⚠️ 為什麼品質門檻設 Q15 / Q20 —— 定序儀的「品質分箱」

**現代 Illumina 定序儀不會輸出連續的品質分數，而是量化到少數幾個「箱」（bin）。**

| 機型 | 品質分箱 |
|------|----------|
| NovaSeq X | 約 {2, 9, 24, 40} |
| NextSeq 2000 | 約 {2, 12, 26, 34} |

這代表：**Q9 到 Q24 之間根本沒有任何鹼基存在。**

所以本 pipeline 所有品質門檻（fastp 的 Q15 / Q20、下游 caller 的
`min-base-quality 10`）**全部落在 Q9–Q24 這個空隙裡**。
意思是：

> 門檻設 10、15 或 20，實際過濾行為**完全一樣** —— 都是「保留 Q24 與 Q40 這兩箱，
> 丟掉 Q2 與 Q9 這兩箱」。

**這件事的重要性**：
- 對評鑑而言，這說明門檻選擇不是隨意的 magic number，而是刻意放在分箱空隙、
  對機型變動不敏感的穩健位置。
- 如果將來要做無損的品質重新編碼（quality re-binning）以節省儲存空間，
  在這些分箱之間重新編碼是**安全的**；但**絕對不能合併最上面兩箱**
  （Q24 與 Q40），那會真正改變下游 caller 的行為。

## 3.4 一個容易踩的坑：DeepVariant 與 HaplotypeCaller 讀的品質不同

- **DeepVariant** 直接讀 BAM 裡的**原始 base quality**，不吃 BQSR recal table。
- **HaplotypeCaller** 在執行時**即時套用** recal table 調整品質。

所以任何「動到 base quality」的變更（例如壓縮、re-binning），
對兩個 caller 的影響路徑是不同的，必須分開驗證。

# 第 4 章：`modules/alignment.nf` — 對位 + 標記重複 + BQSR

## 4.1 這一步在做什麼

`pbrun fq2bam` 是 NVIDIA Parabricks 的旗艦功能：**一個 GPU process 完成 GATK
最佳實踐的前四個步驟**：

```
FASTQ  →  bwa-mem 對位  →  coordinate sort  →  MarkDuplicates  →  BQSR table
                                                                      ↓
                                          輸出：BAM + BAI + recal.txt + duplicate metrics
```

**為什麼用 Parabricks 而不是自己串 bwa + samtools + gatk？**
- 30x WGS 用 CPU 跑完這四步約 20–30 小時；Parabricks 單張 V100 約 3 小時，
  6 張卡（`dgx_single`）約 40 分鐘。
- 結果與 GATK 官方流程**數值一致**（NVIDIA 有發表 concordance 驗證）。
- 少了中間的 BAM 落地，省掉大量 I/O 與磁碟空間。

**授權**：NVIDIA Clara Parabricks 為機構授權（本院已取得），可用於臨床。

## 4.2 全文逐行註解

```groovy
/*
 * =========================================================
 * WGS/WES Germline Analysis Pipeline - Alignment Module
 * =========================================================
 * Author   : Po-Yu Lin (林伯昱)
 * （授權與免責宣告同 main.nf，此處省略）
 * =========================================================
 */

process PARABRICKS_FQ2BAM {
    tag "$meta.id"
    // 實測：RAM 114GB（30x WGS），CPU 2106%（~21 cores）
    // DGX：--low-memory 模式，VRAM 壓到 16GB 以下，單卡跑一個 process，maxForks=6
    // 記憶體由 config withName 個別設定
    label 'process_high'   // CPU / RAM 等級
    label 'process_gpu'    // 【重要】這個 label 讓 config 知道要配 GPU、要限制 maxForks

    publishDir "${params.out_dir}/${meta.id}/02_alignment", mode: 'copy'

    // INPUT:
    //   reads         - fastp 過濾後的 FASTQ pair [R1, R2]
    //   fasta         - hg38 reference genome
    //   known_sites   - BQSR 用的已知變異位點
    //                   四份：dbSNP + Mills indels + GATK known indels + 1000G SNPs
    //
    // 【為什麼索引檔要一個一個宣告？】Nextflow 只會把「宣告成 input 的檔案」
    //   建 symlink 進 work 目錄。bwa 執行時會自己去找 <fasta>.bwt 等檔案，
    //   如果沒宣告，work 目錄裡就沒有那些檔 → bwa 報 "fail to locate the index"。
    input:
    tuple val(meta), path(reads)
    path fasta          // 主序列 .fasta
    path fasta_fai      // .fai（samtools 索引）
    path fasta_dict     // .dict（GATK sequence dictionary）
    path bwa_amb        // bwa 索引 1/5
    path bwa_ann        // bwa 索引 2/5
    path bwa_bwt        // bwa 索引 3/5（最大，約 3 GB）
    path bwa_pac        // bwa 索引 4/5
    path bwa_sa         // bwa 索引 5/5
    path known_sites        // dbSNP 138
    path known_sites_tbi
    path known_sites_2      // Mills gold standard indels
    path known_sites_2_tbi
    path known_sites_3      // GATK known indels
    path known_sites_3_tbi
    path known_sites_4      // 1000G phase1 high-confidence SNPs
    path known_sites_4_tbi

    // OUTPUT:
    //   alignment_bundle - [BAM, BAI, BQSR recalibration table]（後續所有步驟的主要輸入）
    //   qc_metrics       - duplicate metrics（供 MultiQC 使用）
    //   parabricks_qc    - Parabricks 內建 QC metrics 目錄
    //
    // 【為什麼打包成 bundle？】BAM/BAI/recal 三個檔幾乎所有下游都要，
    //   打成一個 tuple 讓下游只要接一個 channel，不用做三次 join。
    output:
    tuple val(meta), path("*.bam"), path("*.bai"), path("*.recal.txt"), emit: alignment_bundle
    path "*.duplicate_metrics.txt",                                     emit: qc_metrics
    path "qc_metrics_dir",                                              emit: parabricks_qc

    script:
    // 1. 動態判斷是否為 WES，如果是，則加入 interval-file 參數
    // 註：${params.wes_targets} 是透過 config 定義的絕對路徑，且已被 Singularity bind
    //
    // 【為什麼 WES 要給 interval？】BQSR 只在捕捉區域內收集統計會更準
    //   （捕捉區域外的稀疏 read 深度太低，誤差模型會被雜訊帶偏）。
    def interval_arg  = params.seq_type == "WES" ? "--interval-file ${params.wes_targets}" : ""

    // 2. 組合標準的 GATK Read Group 字串
    //    【注意】這個變數其實已被下面第 4 點的 per-lane RG 取代，屬於歷史殘留，
    //    不影響行為（真正送進 pbrun 的是 in_fq_args 裡的 rg_str）。
    def rg_string     = "\"@RG\\tID:${meta.id}\\tSM:${meta.id}\\tPL:ILLUMINA\\tLB:lib1\\tPU:${meta.id}\""

    // 3. 接收環境變數中的低記憶體設定等參數（由 profile 的 fq2bam_args 提供）
    def custom_args   = params.fq2bam_args ?: ""

    // 4. reads 現在可能是 [R1a, R2a, R1b, R2b, ...]（多 lane）
    // meta.lanes 是 lane list（如 ['L001', 'L002']），由 main.nf 在 groupTuple 時保留
    // 每兩個 reads 一組配對對應的 lane，產生 unique RG ID
    //
    // 【為什麼每個 lane 要獨立的 @RG？】BQSR 的誤差模型是 **per-read-group** 建立的。
    //   不同 lane 的定序化學狀態不同（試劑批次、流動槽位置），誤差特性也不同。
    //   若所有 lane 共用一個 RG ID，模型會把不同 lane 的誤差平均掉 → 校正效果變差。
    //   MarkDuplicates 也需要 RG 才能正確判斷 optical duplicate。
    def reads_list = reads instanceof List ? reads : [reads]         // 防禦：單 lane 時 reads 可能不是 List
    def lanes_list = meta.lanes instanceof List ? meta.lanes : [meta.lanes ?: 'L001']
    def in_fq_args = reads_list.collate(2).withIndex().collect { pair, idx ->
        // collate(2)：[R1a,R2a,R1b,R2b] → [[R1a,R2a],[R1b,R2b]]
        // withIndex()：加上索引，才能對到 lanes_list 的同一位置
        def r1      = pair[0]
        def r2      = pair[1]
        def lane    = lanes_list[idx] ?: "L${String.format('%03d', idx + 1)}"  // 缺 lane 名就用 L001/L002...
        def rg_id   = "${meta.id}.${lane}"     // RG ID 必須唯一 → 樣本名 + lane
        // @RG 各欄位：
        //   ID = read group 唯一識別（BQSR/MarkDuplicates 用）
        //   SM = sample name（VCF 的樣本欄位名稱就是取這個）
        //   PL = platform（ILLUMINA；caller 會依此調整錯誤模型）
        //   LB = library（判斷 PCR duplicate 的範圍；同一 library 才算 duplicate）
        //   PU = platform unit（flowcell.lane.barcode，最細的批次單位）
        def rg_str  = "\"@RG\\tID:${rg_id}\\tSM:${meta.id}\\tPL:ILLUMINA\\tLB:lib1\\tPU:${rg_id}\""
        "--in-fq ${r1} ${r2} ${rg_str}"        // Parabricks 的多 lane 語法：重複 --in-fq
    }.join(" \\\n        ")                     // 用反斜線換行接起來，讓生成的指令好讀

    // GPU lock 開關：只有 DGX profile 會設定 use_gpu_lock = true
    def use_lock      = params.use_gpu_lock ?: false
    def lock_script   = "/datalake_Intermediate/pipeline/pipeline_code/gpu_lock.sh"
    def unlock_script = "/datalake_Intermediate/pipeline/pipeline_code/gpu_unlock.sh"

    // 要使用的 GPU 數量：dgx_single 設 6，dgx 設 1（預設）
    def num_gpus      = params.fq2bam_num_gpus ?: 1

    // GPU lock 區塊：use_lock=true 時才插入，否則給空字串
    // 注意：lock/unlock 腳本在容器外的 host 上執行，不受 Singularity 影響
    //
    // 【機制說明】見第 15 章。重點：
    //   - eval $(gpu_lock.sh N)  → 腳本印出 `export MY_GPUS=10,11; export CUDA_VISIBLE_DEVICES=10,11`
    //                              eval 執行它，環境變數就設好了
    //   - trap "... " EXIT       → 不管 script 是正常結束、出錯、還是被 kill，
    //                              都會執行 unlock，確保卡一定歸還（這是最關鍵的一行）
    def lock_block = use_lock ? """
    # -------------------------------------------------------
    # GPU Lock：搶 ${num_gpus} 張空閒的 V100
    # -------------------------------------------------------
    eval \$(bash ${lock_script} ${num_gpus})
    echo "[fq2bam] ${meta.id} 取得 GPU \${MY_GPUS}"
    trap "bash ${unlock_script} \${MY_GPUS}; echo '[fq2bam] ${meta.id} 釋放 GPU \${MY_GPUS}'" EXIT
    """ : """
    # -------------------------------------------------------
    # 非 DGX 環境：使用 config 指定的預設 GPU
    # （local/dgm 用 Singularity runOptions 裡的 CUDA_VISIBLE_DEVICES）
    # -------------------------------------------------------
    echo "[fq2bam] ${meta.id} 使用預設 GPU（非 DGX 環境）"
    """

    """
    mkdir -p qc_metrics_dir

    ${lock_block}

    pbrun fq2bam \
        --ref ${fasta} \                                    # 參考基因體
        ${in_fq_args} \                                     # 一或多組 --in-fq R1 R2 "@RG..."
        --out-bam ${meta.id}.aligned.sorted.bam \           # 輸出 BAM（已 coordinate sort、已 markdup）
        --out-recal-file ${meta.id}.recal.txt \             # BQSR 校正表（不直接套用，下游 HC 即時套用）
        --out-duplicate-metrics ${meta.id}.duplicate_metrics.txt \  # 重複率統計 → MultiQC
        --out-qc-metrics-dir qc_metrics_dir \               # Parabricks 內建 QC（insert size 等）
        --knownSites ${known_sites} \                       # BQSR known sites × 4
        --knownSites ${known_sites_2} \
        --knownSites ${known_sites_3} \
        --knownSites ${known_sites_4} \
        ${interval_arg} \                                   # WES 才有：--interval-file capture.bed

        --bwa-options="-Y -K 100000000" \
        #   -Y                 supplementary alignment 用 soft-clip 而非 hard-clip。
        #                      【為什麼？】hard-clip 會把序列從 BAM 裡刪掉，SV caller
        #                      （Delly/Manta）就看不到斷點兩側的序列，抓不到 SV。
        #                      soft-clip 保留序列，只是標記為未對到。
        #   -K 100000000       每個處理批次固定 100 Mbp 的鹼基量。
        #                      【為什麼？】bwa 預設批次大小會隨執行緒數改變，
        #                      導致不同執行緒數跑出「不完全相同」的 BAM。
        #                      固定 -K 後，結果與執行緒數無關 → 可重現性（reproducibility）。
        #                      這是 GATK 官方推薦的 deterministic 設定。

        --fix-mate \                                        # 修正 mate 資訊（MC/MQ tag），
                                                            #   下游 MarkDuplicates 與 SV caller 需要
        --optical-duplicate-pixel-distance 2500 \           # 見下方 4.3
        --num-gpus ${num_gpus} \                            # 用幾張卡
        ${custom_args}                                      # profile 給的額外參數
                                                            #   （--low-memory / --gpusort / --gpuwrite）

    # trap 會在此自動觸發，釋放 GPU lock
    """
    // --optical-duplicate-pixel-distance 2500：NovaSeq/NextSeq 適用
    // HiSeq2000 請改為 100
}
```

## 4.3 ⚠️ `--optical-duplicate-pixel-distance 2500` 的意義

**Optical duplicate（光學重複）** 是定序儀上「同一個 cluster 被誤判成兩個」造成的假重複，
與 PCR duplicate 不同。判斷方法是看兩條 read 在流動槽上的**像素距離**是否小於門檻。

| 流動槽類型 | 機型 | 建議值 |
|-----------|------|--------|
| **Patterned**（有規則排列的奈米井） | NovaSeq、NextSeq | **2500** |
| Non-patterned（隨機分佈） | HiSeq 2000/2500 | 100 |

Patterned 流動槽會有 **ExAmp duplicate**（試劑擴增造成鄰近井被同一分子佔據），
距離可能拉到 2500 像素。用 100 會**嚴重低估**重複率。

> **本院用 NovaSeq → 2500 是正確的。** 換機型時這個值必須跟著改，
> 否則 duplicate rate 會失真（進而影響有效深度的評估）。

## 4.4 為什麼 BQSR 只出 recal table，不直接套用

`fq2bam` 只產生 `*.recal.txt`，**沒有**把校正後的品質寫回 BAM。原因：

1. **HaplotypeCaller 可以即時套用** —— Parabricks 的 `haplotypecaller` 接受
   `--in-recal-file`，執行時在記憶體中套用。不需要落地一份 recalibrated BAM。
2. **DeepVariant 本來就不用 BQSR** —— DV 的 CNN 直接從原始品質與比對特徵學習，
   Google 官方明確建議**不要**對 DV 做 BQSR。
3. **省磁碟** —— 一份 30x WGS BAM 約 60–80 GB，不用存兩份。

# 第 5 章：`modules/alignment_qc.nf` — 對位品質 QC

## 5.1 這一章的三個 process

| Process | 工具 | 產出 | 回答什麼問題 |
|---------|------|------|------------|
| `SAMTOOLS_STATS` | samtools stats | `*.stats` | 對位率、錯誤率、insert size、mapping quality 分佈 |
| `MOSDEPTH` | mosdepth | `*.summary.txt` 等 | 深度夠不夠？覆蓋均勻嗎？多少比例達到 20×？ |
| `PLOIDY_CHECK` | 自寫 Python | `*.ploidy.vcf.gz`、`*.ploidy_qc.txt` | 性別對不對？有沒有非整倍體？ |

三者由 `ALIGNMENT_QC` sub-workflow 包起來，`main.nf` 只呼叫一次。

## 5.2 ⚠️ 一個設計決定：QC 統一走 mosdepth

早期實作中，**WES 的倍體判斷是取 gCNV 的 contig-ploidy 結果，WGS 走 mosdepth**，
兩條路徑輸出格式不同、數值定義也不同，難以互相比較，也不好寫進 QC 報告。

**現在的做法：不分 WES/WGS，倍體 QC 一律走 mosdepth 的 per-contig 平均深度。**
gCNV 內部仍然會算自己的 ploidy（那是 gCNV 演算法的必要步驟，不能拿掉），
但**QC 報告只看 mosdepth 那一份**，確保 WES 與 WGS 的 QC 指標定義一致。

## 5.3 全文逐行註解

```groovy
/*
 * =========================================================
 * WGS/WES Germline Analysis Pipeline - Alignment QC Module
 * =========================================================
 * Author   : Po-Yu Lin (林伯昱)
 * （授權與免責宣告同 main.nf，此處省略）
 * =========================================================
 */

// ══════════════════════════════════════════════════════════════════════
// 【Process 1】SAMTOOLS_STATS —— 對位基本統計
//
// 產生 MultiQC 能解析的完整對位統計：
//   - reads mapped / properly paired / singletons 的數量與比例
//   - error rate（依 NM tag 估的 mismatch 率）
//   - insert size 分佈（判斷建庫片段大小是否正常）
//   - MAPQ 分佈（判斷 multi-mapping 的比例）
//   - GC 含量分佈（判斷 GC bias）
// 這些是評鑑「定序品質是否合格」最直接的證據。
// ══════════════════════════════════════════════════════════════════════
process SAMTOOLS_STATS {
    tag "$meta.id"
    // 實測：RAM 9.5MB，CPU ~100%（單核）
    label 'process_low'

    publishDir "${params.out_dir}/${meta.id}/03_alignment_qc", mode: 'copy'

    // INPUT:
    //   alignment_bundle - [BAM, BAI, recal.txt]
    //   （recal.txt 在此不使用，但需維持 tuple 結構）
    //
    // 【Nextflow 慣例】即使不用，也要在 input 宣告完整的 tuple 形狀，
    //   否則 channel 的元素數對不上會直接報錯。
    input:
    tuple val(meta), path(bam), path(bai), path(recal)

    // OUTPUT:
    //   stats - samtools stats 文字報告（mapping rate, error rate 等）（供 MultiQC 使用）
    output:
    path "*.stats", emit: stats

    script:
    // 保留 1 個 thread 給主程式，剩下的給解壓縮
    //   samtools 的 -@ 指的是「額外的」解壓縮執行緒，不含主執行緒
    def threads = task.cpus > 1 ? task.cpus - 1 : 1
    """
    samtools stats -@ ${threads} ${bam} > ${meta.id}.stats
    """
}


// ══════════════════════════════════════════════════════════════════════
// 【Process 2】MOSDEPTH —— 深度與覆蓋度
//
// 為什麼用 mosdepth 而不是 GATK DepthOfCoverage / bedtools genomecov？
//   - 快 10–100 倍（用 BAM index 的 chunk 直接算，不逐鹼基掃）
//   - 記憶體固定（~2GB），不隨基因體大小成長
//   - 原生支援 --thresholds，一次算出「≥1× / ≥10× / ≥20× ... 的鹼基比例」
//   - MIT 授權，可商用
//
// ⚠️ 一個必須知道的行為：mosdepth 對「不在 --by BED 裡的 contig」
//   會在 summary 輸出 `<contig>_region  0.00` 的列。這不代表深度真的是 0，
//   只代表「這條 contig 沒有被 --by 涵蓋」。ploidy_check.py 必須處理這件事
//   （見第 13 章的 fallback 邏輯）。
// ══════════════════════════════════════════════════════════════════════
process MOSDEPTH {
    tag "$meta.id"
    // 實測：RAM 1.9GB，CPU 239%（~2-3 cores）
    label 'process_low'

    publishDir "${params.out_dir}/${meta.id}/03_alignment_qc", mode: 'copy'

    // INPUT:
    //   alignment_bundle - [BAM, BAI, recal.txt]
    //   targets          - WES: capture BED；WGS: 'NO_FILE'（pipeline 自動判斷）
    input:
    tuple val(meta), path(bam), path(bai), path(recal)
    path targets
    path autosome_bed   // WGS 深度 QC 用的 autosome BED（chr1-22），由 main.nf 傳入
                        // WES 傳 NO_FILE（WES 用 capture BED 就已限制範圍）
                        //
                        // 【Nextflow 技巧】'NO_FILE' 是一個約定的假檔名。
                        //   Nextflow 的 path input 不接受 null，所以用一個不存在的
                        //   檔名當哨兵值，script 裡再用 targets.name != 'NO_FILE' 判斷。

    // OUTPUT:
    //   global_dist    - 全基因組深度分布（供 MultiQC 使用）
    //   summary        - 各染色體深度摘要（WES 的 _region 行 = target region 真實深度）
    //   修改輸出：移除了 per-base，新增了 thresholds 和 regions
    output:
    path "*.global.dist.txt",     emit: global_dist
    tuple val(meta), path("*.summary.txt"), emit: summary   // 帶 meta，PLOIDY_CHECK 要用 meta.sex
    path "*.thresholds.bed.gz*",  emit: thresholds   // 包含 .gz 和 .csi 索引
                                                     //   （* 萬用字元一次收 .gz 與 .gz.csi）
    path "*.regions.bed.gz*",     emit: regions      // 這是由 --by 產生的區塊深度

    script:
    // WES：用 capture BED 做 --by，summary 的 _region 行才是真實 target 深度
    // WGS：用 autosome BED（chr1-22）做 --by，排除 chrM/chrX/chrY/unplaced
    //      這是國際標準做法，避免 chrM 高拷貝數和性別染色體深度差異污染 QC 指標
    //
    // 【為什麼 WGS 的 mean coverage 要排除 chrM/chrX/chrY？】
    //   - chrM 每個細胞有數百到數千個拷貝 → 深度可能是核基因體的 100–1000 倍，
    //     混進去算平均會嚴重高估
    //   - chrX/chrY 的深度隨性別而異（男性各半），混進去會讓男女樣本的
    //     "mean coverage" 不可比
    //   - unplaced/alt contig 的對位品質差，深度不可靠
    def by_cmd = (targets.name != 'NO_FILE')         ? "--by ${targets}"         : "--by ${autosome_bed}"
    """
    mosdepth \
        --threads ${task.cpus} \                  # 解壓縮執行緒
        ${by_cmd} \                               # WES: capture BED；WGS: autosome BED
        --no-per-base \                           # 不輸出逐鹼基深度（那個檔可以到數 GB，用不到）
        --thresholds 1,10,15,20,30,50,100 \       # 算「≥N× 的鹼基比例」的門檻列表
                                                  #   臨床常用：WES 看 ≥20×，WGS 看 ≥15×/≥30×
        --flag 1796 \                             # 排除的 SAM flag 位元和（1796 = 4+256+512+1024）
                                                  #   4    = read unmapped（未對到）
                                                  #   256  = not primary alignment（次要對位）
                                                  #   512  = read fails vendor QC（定序儀判定失敗）
                                                  #   1024 = PCR or optical duplicate（重複）
                                                  #   → 只算「真正可用」的 read，這是業界標準值
        ${meta.id} \                              # 輸出檔名前綴
        ${bam}
    """
}


// ──────────────────────────────────────────────────────────────
// PLOIDY_CHECK：從 mosdepth summary 推 sex/ploidy（sex 防呆 + aneuploidy 提示）。
//   warn-only：只印警示 + 出 QC 檔，不改 ploidy、不讓 pipeline 失敗。
//   輸出（對齊 DRAGEN *.ploidy.vcf.gz 風格）：
//     - <id>.ploidy.vcf.gz ：每條 contig 一列 FORMAT=DC:NDC，header 帶 estimated/declared 核型
//     - <id>.ploidy_qc.txt ：人可讀摘要 + WARNINGS
//   ploidy_check.py 以 staged path input 傳入（content-hash → 改 script 後 -resume 正確重跑）。
//
// 【為什麼要做這個檢查？】三個實際會發生的問題：
//   1. Samplesheet 性別填錯（打字錯誤、病歷登錄錯誤）→ 下游 +fixploidy 會把
//      男性 chrX 錯誤地當雙套（或反之），產生假的雜合/純合基因型。
//   2. 檢體對調 → 性別不符是最快發現的訊號。
//   3. 真實的性染色體非整倍體（Turner 45,X / Klinefelter 47,XXY）→ 這本身就是
//      臨床發現，必須提示，不能默默當成 QC 失敗。
//
// 【為什麼是 warn-only 而不是讓 pipeline 失敗？】
//   因為第 3 種情況（真實非整倍體）是「正確的結果」，不是錯誤。
//   自動停掉 pipeline 會讓真實病例跑不完。所以只出警示，由人判讀。
//
// 【為什麼用 staged path input 傳 .py 而不是寫死路徑？】
//   Nextflow 的 -resume 是靠「input 的 content hash」判斷要不要重跑。
//   把 .py 宣告成 path input，改了腳本內容 → hash 變 → 自動重跑。
//   若寫死絕對路徑，改腳本 Nextflow 不會察覺，-resume 會沿用舊結果（錯誤的快取命中）。
// ──────────────────────────────────────────────────────────────
process PLOIDY_CHECK {

    tag "${meta.id}"

    publishDir "${params.out_dir}/${meta.id}/03_alignment_qc", mode: 'copy'

    input:
    tuple val(meta), path(summary)   // 來自 MOSDEPTH.out.summary
    path ploidy_py                   // scripts/ploidy_check.py（見第 13 章）

    output:
    tuple val(meta),
          path("${meta.id}.ploidy.vcf.gz"),
          path("${meta.id}.ploidy_qc.txt"), emit: ploidy

    script:
    """
    python3 ${ploidy_py} \
        --summary ${summary} \                    # mosdepth 的 *.summary.txt
        --sample ${meta.id} \                     # 樣本名（寫進 VCF 的樣本欄位）
        --declared-sex ${meta.sex} \              # samplesheet 宣告的性別（拿來比對）
        --seq-type ${params.seq_type} \           # WES/WGS（判斷門檻不同）
        --out-vcf ${meta.id}.ploidy.vcf \         # 機器可讀（對齊 DRAGEN 格式）
        --out-qc ${meta.id}.ploidy_qc.txt         # 人可讀摘要 + WARNINGS
    # 對齊 DRAGEN 的 *.ploidy.vcf.gz（用 bcftools 壓縮；tertiary_python 容器含 bcftools）
    #   【為什麼用 bcftools 而不是 bgzip？】容器裡有 bcftools 但不一定有獨立的 bgzip；
    #   bcftools view -Oz 效果相同（BGZF 壓縮）。
    bcftools view ${meta.id}.ploidy.vcf -Oz -o ${meta.id}.ploidy.vcf.gz
    rm -f ${meta.id}.ploidy.vcf                   # 只留壓縮版，避免重複佔空間
    """
}


// ──────────────────────────────────────────────────────────────
// ALIGNMENT_QC sub-workflow（Step 3）：SAMTOOLS_STATS + MOSDEPTH + PLOIDY_CHECK。
//   對外只吃 bam_ch；mosdepth targets / autosome BED / ploidy_check.py 於內部依 params 建立。
//   emit MultiQC 需要的 stats / summary / global_dist，及 ploidy QC 輸出。
//
// 【sub-workflow 的價值】main.nf 只要寫 `ALIGNMENT_QC(ch_bam)` 一行。
//   「WES 要傳 capture BED、WGS 要傳 autosome BED」這種細節完全收在這裡，
//   main.nf 不需要知道，也不需要準備那些 channel。
// ──────────────────────────────────────────────────────────────
workflow ALIGNMENT_QC {
    take:
    bam_ch      // tuple(meta, bam, bai, ...)

    main:
    // WES 用 capture BED 限制範圍；WGS 傳哨兵值 NO_FILE
    ch_mosdepth_targets = (params.seq_type == "WES") ?
        file(params.wes_targets) : file("NO_FILE")
    // WGS 深度 QC 只看 autosome primary contig（chr1-22）；排除 chrM/chrX/chrY/unplaced
    ch_autosome_bed = (params.seq_type == "WGS") ?
        file(params.autosome_bed) : file("NO_FILE")
    // projectDir = main.nf 所在目錄；用它組路徑，不管在哪裡執行都找得到
    ch_ploidy_py = file("${projectDir}/scripts/ploidy_check.py")

    SAMTOOLS_STATS(bam_ch)
    MOSDEPTH(bam_ch, ch_mosdepth_targets, ch_autosome_bed)
    PLOIDY_CHECK(MOSDEPTH.out.summary, ch_ploidy_py)

    emit:
    stats       = SAMTOOLS_STATS.out.stats
    summary     = MOSDEPTH.out.summary      // mito NuMT filter 與 MultiQC 共用
    global_dist = MOSDEPTH.out.global_dist
    thresholds  = MOSDEPTH.out.thresholds
    regions     = MOSDEPTH.out.regions
    ploidy      = PLOIDY_CHECK.out.ploidy
}
```

## 5.4 輸出檔案速查（`03_alignment_qc/`）

| 檔案 | 內容 | 評鑑會問什麼 |
|------|------|------------|
| `<id>.stats` | samtools 完整統計 | 對位率（應 >99%）、properly paired 率、error rate |
| `<id>.mosdepth.global.dist.txt` | 全基因體深度累積分佈 | 「多少比例的基因體達到 N×」的曲線資料 |

# 第 6 章：SNV / indel 呼叫與 ensemble

## 6.1 整體架構：為什麼要跑兩個 caller

```
                 BAM + recal.txt
                       │
        ┌──────────────┴──────────────┐
        │                             │
   DeepVariant                 HaplotypeCaller
   （CNN 深度學習）              （haplotype 重組 + 貝氏）
        │                             │
        │                        WGS: VQSR SNP → VQSR INDEL
        │                        WES: 直接用 raw（變異數不足，VQSR 訓不起來）
        │                             │
        └──────────┬──────────────────┘
                   │
        （選用 --run_phasing）
        各 caller 各自 WhatsHap phase + combine_phased.py 合成 compound
                   │
             BCFTOOLS_ENSEMBLE
             （header 修正 → norm 拆多等位 → merge → +fixploidy）
                   │
            ensemble.fixed.vcf.gz  → 三級分析讀這一份
```

**為什麼兩個 caller？**

| | DeepVariant | HaplotypeCaller |
|---|---|---|
| 原理 | 把 pileup 畫成影像，用 CNN 分類 | 局部重組 haplotype，PairHMM + 貝氏 |
| 強項 | 低品質區、複雜 indel、對系統性誤差穩健 | 明確的統計模型、註記豐富（可做 VQSR） |
| 弱項 | 訓練資料以外的情境（非人類、罕見平台） | 高重複區、長 indel |
| **錯誤模式** | **與 HC 不相關** | **與 DV 不相關** |

關鍵在最後一列：兩者的**錯誤模式不相關**。兩個都叫到的變異，
假陽性機率是兩者的乘積（極低）；只有一個叫到的，三級分析會在 `CALLERS` 欄位
標記來源，由判讀者決定。這比單一 caller 的「相信或不相信」二分法資訊量高很多。

## 6.2 `modules/call_snv.nf` 全文逐行註解

```groovy
/*
 * =========================================================
 * WGS/WES Germline Analysis Pipeline
 * modules/call_snv.nf
 * =========================================================
 * SNV/indel calling ＋ ensemble sub-workflow（原 Lane 1 / 2 ＋ Step 5 的 phasing/ensemble）。
 *
 * 多 process 的 caller 各自為第二層 sub-workflow：
 *   DEEPVARIANT     = PARABRICKS_DEEPVARIANT → BGZIP_VCF_DV
 *   HAPLOTYPECALLER = PARABRICKS_HAPLOTYPECALLER → BGZIP_VCF_HC
 *   VQSR（WGS only） = GATK_VQSR_SNP → GATK_VQSR_INDEL
 * 之後 PHASE_COMBINE（現有 sub-workflow，--run_phasing 時，各 caller 先 phase+combine）
 *   → BCFTOOLS_ENSEMBLE（reheader/norm/merge/+fixploidy）→ ensemble.fixed。
 *
 * 【為什麼要獨立一個 module 檔？】
 * 需跨 module 且對 BGZIP_VCF / BCFTOOLS_STATS 取兩次別名，故獨立成一個 module 檔
 * （Nextflow 無法對同檔內定義的 process 取別名）。
 *   → 也就是說：`include { BGZIP_VCF as BGZIP_VCF_DV }` 這種寫法，
 *     只有在「從別的檔案 include 進來」時才成立。若 process 定義在同一個檔案裡，
 *     Nextflow 不允許取別名，就沒辦法讓 DV 和 HC 各用一份獨立的 BGZIP_VCF。
 *
 * emit：
 *   dv_vcf         → CALL_CNV_SV（CNVkit 的 SNP b-allele 輸入）
 *   hc_vcf_raw     → CALL_ROH（保留 GT/AD 的 HC 原始 VCF）
 *   ensemble       → 發布 04_snv_indel + 三級讀取
 *   dv_stats / ensemble_stats → MultiQC
 */

// 從 variant_calling.nf 引入四個 process
include { PARABRICKS_DEEPVARIANT;
          PARABRICKS_HAPLOTYPECALLER;
          GATK_VQSR_SNP;
          GATK_VQSR_INDEL }                 from './variant_calling'
// 從 postprocessing.nf 引入，並對兩個 process 各取兩個別名
//   BGZIP_VCF        → BGZIP_VCF_DV / BGZIP_VCF_HC（DAG 上才分得出是哪一路）
//   BCFTOOLS_STATS   → BCFTOOLS_STATS（DV 用）/ BCFTOOLS_STATS_ENSEMBLE（ensemble 用）
include { BGZIP_VCF as BGZIP_VCF_DV;
          BGZIP_VCF as BGZIP_VCF_HC;
          BCFTOOLS_ENSEMBLE;
          BCFTOOLS_STATS;
          BCFTOOLS_STATS as BCFTOOLS_STATS_ENSEMBLE } from './postprocessing'
include { PHASE_COMBINE }                   from './phasing'


// ── DeepVariant（GPU）→ bgzip ─────────────────────────────────
// 【為什麼要包成 sub-workflow？】DeepVariant 輸出未壓縮的 .vcf，
//   下游都需要 .vcf.gz + .tbi。把「call + 壓縮」綁成一個邏輯單位，
//   呼叫端就只要拿一個「已壓縮已索引」的 channel，不用自己記得補壓縮。
workflow DEEPVARIANT {
    take:
    bam_ch
    fasta
    fasta_fai
    fasta_dict

    main:
    PARABRICKS_DEEPVARIANT(bam_ch, fasta, fasta_fai, fasta_dict)
    BGZIP_VCF_DV(PARABRICKS_DEEPVARIANT.out.vcf)

    emit:
    vcf = BGZIP_VCF_DV.out.vcf   // tuple(meta, vcf.gz, tbi)
}

// ── HaplotypeCaller（GPU）→ bgzip。bam_ch 應已 join 過 DV 輸出（同張 GPU 序列化）──
// 【注意這個註解的含意】呼叫端（CALL_SNV）會刻意讓 HC 等 DV 跑完才開始，
//   避免兩個 GPU process 同時搶同一張卡的 VRAM。細節見 6.4。
workflow HAPLOTYPECALLER {
    take:
    bam_ch
    fasta
    fasta_fai
    fasta_dict

    main:
    PARABRICKS_HAPLOTYPECALLER(bam_ch, fasta, fasta_fai, fasta_dict)
    BGZIP_VCF_HC(PARABRICKS_HAPLOTYPECALLER.out.vcf)

    emit:
    vcf = BGZIP_VCF_HC.out.vcf
}

// ── VQSR（WGS）：SNP → INDEL；resource 檔內部依 params 建立 ──────
// 【為什麼 SNP 先、INDEL 後？】VQSR 是 mode-specific 的：SNP 模型只重新標記 SNP 的
//   FILTER 欄，INDEL 的 FILTER 保持不動。所以第二步吃第一步的輸出，兩種標記都會留下。
//   反過來做結果一樣，但 Broad 的順序慣例是 SNP 先。
workflow VQSR {
    take:
    hc_vcf
    fasta
    fasta_fai
    fasta_dict

    main:
    // 【設計】resource 檔在 sub-workflow 內部用 file(params.X) 建立，
    //   呼叫端不需要準備這 8 個 channel。換 resource 只改 config。
    GATK_VQSR_SNP(
        hc_vcf,
        fasta, fasta_fai, fasta_dict,
        file(params.hapmap),     file("${params.hapmap}.tbi"),      // truth set
        file(params.omni),       file("${params.omni}.tbi"),        // training
        file(params.known_snps), file("${params.known_snps}.tbi"),  // training
        file(params.dbsnp),      file("${params.dbsnp}.tbi")        // known（只做 novel/known 分層）
    )
    GATK_VQSR_INDEL(
        GATK_VQSR_SNP.out.vcf,   // ← 吃上一步的輸出
        fasta, fasta_fai, fasta_dict,
        file(params.known_indels), file("${params.known_indels}.tbi"),  // Mills truth set
        file(params.axiom),        file("${params.axiom}.tbi"),         // training
        file(params.dbsnp),        file("${params.dbsnp}.tbi")
    )

    emit:
    vcf = GATK_VQSR_INDEL.out.vcf
}


// ══════════════════════════════════════════════════════════════════════
// 【主 sub-workflow】CALL_SNV
// ══════════════════════════════════════════════════════════════════════
workflow CALL_SNV {
    take:
    bam_ch      // tuple(meta, bam, bai, recal)

    main:
    ch_fasta      = file(params.fasta)
    ch_fasta_fai  = file("${params.fasta}.fai")
    ch_fasta_dict = file(params.fasta.replace('.fasta', '.dict'))

    // Lane 1: DeepVariant
    DEEPVARIANT(bam_ch, ch_fasta, ch_fasta_fai, ch_fasta_dict)
    ch_dv_vcf = DEEPVARIANT.out.vcf

    // Lane 2a: HaplotypeCaller（等 DV 發射後才觸發，避免同張 GPU 同時佔用）
    //
    // 【這段在做什麼？】人工製造一個「假的資料相依」，強迫 HC 排在 DV 之後。
    //   Nextflow 的排程是資料驅動的：只要 input channel 有東西就會開跑。
    //   DV 和 HC 都只吃 bam_ch → 它們會同時開跑 → 同一張 GPU 上兩個 Parabricks
    //   process 搶 VRAM → CUDA OOM。
    //
    //   解法：把 bam_ch 跟「DV 的輸出」做 join。DV 沒吐出東西之前，
    //   join 不會發射任何元素，HC 自然就不會開始。
    //   map 到 meta.id 只是為了讓 join 的第二個元素輕量（不搬 VCF 檔案物件）。
    ch_bam_after_dv = bam_ch
        .join(ch_dv_vcf.map { meta, vcf, tbi -> [meta, meta.id] })   // [meta, bam, bai, recal, meta.id]
        .map { meta, bam, bai, recal, dummy -> [meta, bam, bai, recal] }  // 把 dummy 丟掉，還原成原形狀
    HAPLOTYPECALLER(ch_bam_after_dv, ch_fasta, ch_fasta_fai, ch_fasta_dict)
    ch_hc_vcf_raw = HAPLOTYPECALLER.out.vcf

    // Lane 2b: VQSR（WGS）；WES 直接用 raw
    //
    // 【為什麼 WES 不做 VQSR？】VQSR 是用「這個樣本自己的變異」去訓練高斯混合模型。
    //   WGS 一個樣本約 400–500 萬個變異，訓練資料充足。
    //   WES 只有 3–5 萬個，其中落在 truth set 的更少 → 模型訓不起來，
    //   GATK 官方明確建議 WES 單樣本改用 hard filter 或 joint calling。
    //   本 pipeline 的處理：WES 不做 VQSR，交給 ensemble 的雙 caller 一致性
    //   與三級分析的 ACMG 過濾把關。
    if (params.seq_type == "WGS") {
        VQSR(ch_hc_vcf_raw, ch_fasta, ch_fasta_fai, ch_fasta_dict)
        ch_filtered_hc_vcf = VQSR.out.vcf
    } else {
        ch_filtered_hc_vcf = ch_hc_vcf_raw
    }

    // Step 5:（選用 --run_phasing）各 caller 先 phase+combine 再進 ensemble；否則直接 join。
    //   在 merge「之前」、各 caller 還單樣本 biallelic 時做，compound（SUZ12）才 phase/合得成。
    //   （為什麼一定要在 merge 之前，見第 7 章）
    if (params.run_phasing) {
        ch_combine_py = file("${projectDir}/scripts/combine_phased.py")
        // 把兩個 caller 的 VCF 混成一條 channel，各自貼上 'DV' / 'HC' 標籤。
        // 【為什麼要混成一條？】這樣 PHASE_COMBINE 只需要寫一次，
        //   兩個 caller 的資料自然平行跑（Nextflow 會為每個元素開一個 task）。
        ch_callers = ch_dv_vcf.map { meta, vcf, tbi -> tuple(meta, 'DV', vcf, tbi) }
            .mix( ch_filtered_hc_vcf.map { meta, vcf, tbi -> tuple(meta, 'HC', vcf, tbi) } )
        PHASE_COMBINE(ch_callers, bam_ch, ch_fasta, ch_fasta_fai, ch_combine_py)

        // 跑完再依標籤拆回兩條，去掉標籤還原成 tuple(meta, vcf, tbi)
        ch_dv_ready = PHASE_COMBINE.out.vcf
            .filter { it[1] == 'DV' }.map { meta, c, vcf, tbi -> tuple(meta, vcf, tbi) }
        ch_hc_ready = PHASE_COMBINE.out.vcf
            .filter { it[1] == 'HC' }.map { meta, c, vcf, tbi -> tuple(meta, vcf, tbi) }
        ch_ensemble_input = ch_dv_ready.join(ch_hc_ready, by: 0)   // by: 0 = 用 meta 當鍵配對
    } else {
        // join() 確保同一樣本的 DV/HC 配對（多樣本非同步完成不會跨樣本錯配）
        //
        // 【為什麼一定要 join 而不能用 merge/combine？】跑多個樣本時，
        //   A 樣本的 DV 可能比 B 樣本的 HC 晚完成。若用 merge（按到達順序配對），
        //   會把 A 的 DV 跟 B 的 HC 配在一起 → 災難性錯誤，而且不會報錯。
        //   join 是用「鍵值」（這裡是 meta）配對，絕對不會錯配。
        ch_ensemble_input = ch_dv_vcf.join(ch_filtered_hc_vcf, by: 0)
    }

    // 性別感知倍體定義（單一真相來源；+fixploidy 用）
    ch_sex_ploidy = file(params.sex_ploidy_file)
    BCFTOOLS_ENSEMBLE(ch_ensemble_input, ch_sex_ploidy)

    // 統計（→ MultiQC）
    BCFTOOLS_STATS(ch_dv_vcf)                              // DV 單獨的統計
    BCFTOOLS_STATS_ENSEMBLE(BCFTOOLS_ENSEMBLE.out.vcf)     // 合併後的統計

    emit:
    dv_vcf         = ch_dv_vcf              // → CNVkit（B-allele frequency）
    hc_vcf_raw     = ch_hc_vcf_raw          // → ROH（未經 VQSR，GT/AD 完整）
    ensemble       = BCFTOOLS_ENSEMBLE.out.vcf   // → 三級分析
    dv_stats       = BCFTOOLS_STATS.out.stats
    ensemble_stats = BCFTOOLS_STATS_ENSEMBLE.out.stats
}
```

## 6.3 `modules/variant_calling.nf` 全文逐行註解

```groovy
/*
 * =========================================================
 * WGS/WES Germline Analysis Pipeline - Variant Calling Module
 * =========================================================
 * Author   : Po-Yu Lin (林伯昱)
 * （授權與免責宣告同 main.nf，此處省略）
 * =========================================================
 */

// ══════════════════════════════════════════════════════════════════════
// 【Process 1】PARABRICKS_DEEPVARIANT
//
// Lane 1: DeepVariant（GPU）
// 深度學習 SNP/Indel caller，對 WGS/WES 均有高 sensitivity
// 實測：RAM 27.6GB，CPU 3111%（~31 cores）
// 記憶體由 config withName 個別設定為 32GB
//
// 【DeepVariant 的原理，用一句話說】
//   把某個位點附近的 read pileup「畫成一張多通道影像」
//   （通道 = 鹼基、品質、strand、是否支持 ALT…），
//   丟給 CNN 分類成 {hom-ref, het, hom-alt}。
//   完全不用手工設計統計模型 → 對「訓練資料涵蓋過的」情境非常穩健。
//
// 【重要】DeepVariant **不吃 BQSR recal table**。
//   Google 官方明確說明 DV 的模型已經隱含學會了系統性誤差，
//   額外做 BQSR 反而會降低準確度。所以這裡 input 雖然收了 recal_table，
//   pbrun 指令中並沒有用到它（只是為了維持 tuple 形狀）。
// ══════════════════════════════════════════════════════════════════════
process PARABRICKS_DEEPVARIANT {
    tag "$meta.id"
    label 'process_high'
    label 'process_gpu'
    // 【注意】這個 process 沒有 publishDir —— DV 的原始 VCF 不對外發布，
    //   對外的是壓縮後（BGZIP_VCF_DV）與合併後（ensemble）的版本。

    // INPUT:
    //   alignment_bundle - [BAM, BAI, recal.txt]
    //   fasta/fai/dict   - hg38 reference + index
    input:
    tuple val(meta), path(bam), path(bai), path(recal_table)   // recal_table 收了但不用（見上）
    path fasta
    path fasta_fai
    path fasta_dict

    // OUTPUT:
    //   vcf - DeepVariant genotyped VCF（壓縮 + tabix index）
    output:
    // 輸出標準 VCF，以便後續與 HaplotypeCaller 進行 Ensemble Calling (bcftools isec)
    tuple val(meta), path("*.deepvariant.vcf"), emit: vcf   // 未壓縮，下一步 BGZIP_VCF 壓

    script:
    // 動態判斷 WES 專用參數
    def interval_arg  = params.seq_type == "WES" ? "--interval-file ${params.wes_targets}" : ""
    // 【重要】--use-wes-model：DeepVariant 有 WGS / WES / PacBio 等不同訓練模型。
    //   WES 的深度分佈、捕捉邊界的覆蓋衰減特性與 WGS 完全不同，
    //   用錯模型會明顯降低準確度（尤其在 exon 邊界）。
    def model_arg     = params.seq_type == "WES" ? "--use-wes-model" : ""

    // GPU lock（同 alignment.nf，機制見第 15 章）
    def use_lock      = params.use_gpu_lock ?: false
    def lock_script   = "/datalake_Intermediate/pipeline/pipeline_code/gpu_lock.sh"
    def unlock_script = "/datalake_Intermediate/pipeline/pipeline_code/gpu_unlock.sh"
    def num_gpus      = params.dv_num_gpus ?: 1

    def lock_block = use_lock ? """
    eval \$(bash ${lock_script} ${num_gpus})
    echo "[deepvariant] ${meta.id} 取得 GPU \${MY_GPUS}"
    trap "bash ${unlock_script} \${MY_GPUS}; echo \'[deepvariant] ${meta.id} 釋放 GPU \${MY_GPUS}\'" EXIT
    """ : """
    echo "[deepvariant] ${meta.id} 使用預設 GPU（非 DGX 環境）"
    """

    """
    echo "Waiting 30s for GPU memory cleanup..."
    sleep 30
    # 【為什麼要 sleep 30？】上一個 GPU process 結束後，CUDA driver 釋放 VRAM
    # 不是瞬間的（尤其是被 OOM killer 砍掉時）。立刻啟動下一個 Parabricks
    # 有機會撞到「VRAM 還沒還乾淨」而 CUDA OOM。30 秒是實測夠用的緩衝。

    ${lock_block}

    pbrun deepvariant \
        --ref ${fasta} \
        --in-bam ${bam} \
        --out-variants ${meta.id}.deepvariant.vcf \
        ${interval_arg} \                      # WES: --interval-file capture.bed
        ${model_arg} \                         # WES: --use-wes-model
        --num-gpus ${num_gpus}

    # trap 會在此自動觸發，釋放 GPU lock
    """
}

// ══════════════════════════════════════════════════════════════════════
// 【Process 2】PARABRICKS_HAPLOTYPECALLER
//
// Lane 2a: HaplotypeCaller（GPU）
// GATK HaplotypeCaller 的 GPU 加速版
// 實測：RAM 20.7GB，CPU 1435%（~14 cores）
// 記憶體由 config withName 個別設定為 24GB
//
// 【HaplotypeCaller 的原理，用一句話說】
//   在每個「活躍區域」（有變異跡象的地方）重新組裝出所有可能的 haplotype，
//   用 PairHMM 算每條 read 支持每個 haplotype 的機率，
//   再用貝氏模型推出最可能的基因型。
//   優點：對 indel 與複雜區的處理有明確的統計基礎，且輸出豐富的註記
//   （QD/FS/SOR/MQRankSum…），這些註記正是 VQSR 的訓練特徵。
// ══════════════════════════════════════════════════════════════════════
process PARABRICKS_HAPLOTYPECALLER {
    tag "$meta.id"
    label 'process_high'
    label 'process_gpu'

    // INPUT:
    //   alignment_bundle - [BAM, BAI, recal.txt]（recal.txt 用於 BQSR on-the-fly）
    //   fasta/fai/dict   - hg38 reference + index
    input:
    tuple val(meta), path(bam), path(bai), path(recal_table)   // ← 這裡 recal_table 是真的會用
    path fasta
    path fasta_fai
    path fasta_dict

    // OUTPUT:
    //   vcf - HaplotypeCaller genotyped VCF（壓縮 + tabix index）
    output:
    tuple val(meta), path("*.haplotypecaller.vcf"), emit: vcf

    script:
    // 動態判斷：如果是 WES，自動加入 Capture Kit BED 檔限制運算範圍
    def interval_arg  = params.seq_type == "WES" ? "--interval-file ${params.wes_targets}" : ""
    // 抓取 config 裡的 htvc_args，若無定義則留空
    //   DGM 會給 "--htvc-low-memory"（16GB VRAM 的機器需要）
    def custom_args   = params.htvc_args ?: ""

    def use_lock      = params.use_gpu_lock ?: false
    def lock_script   = "/datalake_Intermediate/pipeline/pipeline_code/gpu_lock.sh"
    def unlock_script = "/datalake_Intermediate/pipeline/pipeline_code/gpu_unlock.sh"
    def num_gpus      = params.htvc_num_gpus ?: 1

    def lock_block = use_lock ? """
    eval \$(bash ${lock_script} ${num_gpus})
    echo "[haplotypecaller] ${meta.id} 取得 GPU \${MY_GPUS}"
    trap "bash ${unlock_script} \${MY_GPUS}; echo \'[haplotypecaller] ${meta.id} 釋放 GPU \${MY_GPUS}\'" EXIT
    """ : """
    echo "[haplotypecaller] ${meta.id} 使用預設 GPU（非 DGX 環境）"
    """

    """
    echo "Waiting 30s for GPU memory cleanup..."
    sleep 30

    ${lock_block}

    pbrun haplotypecaller \
        --ref ${fasta} \
        --in-bam ${bam} \
        --in-recal-file ${recal_table} \       # 【重點】即時套用 BQSR，不需要落地 recalibrated BAM
        --out-variants ${meta.id}.haplotypecaller.vcf \
        -G StandardAnnotation \                # 標準註記組：QD, FS, SOR, MQ, MQRankSum, ReadPosRankSum...
        -G StandardHCAnnotation \              # HC 專屬註記：DP, AD, GQ...
                                               #   【為什麼要明確指定？】VQSR 需要這些註記當特徵。
                                               #   少一個註記，VariantRecalibrator 就會報錯或降級。
        ${interval_arg} \
        --num-gpus ${num_gpus} \
        ${custom_args}                         # DGM: --htvc-low-memory

    # trap 會在此自動觸發，釋放 GPU lock
    """
}

// ══════════════════════════════════════════════════════════════════════
// 【Process 3】GATK_HAPLOTYPECALLER（CPU 備援，目前未接進主流程）
//
// Lane 2a（備用）: HaplotypeCaller CPU
// 無 GPU 時的替代方案，結果與 GPU 版相同
//
// ⚠️【一個曾經存在的 bug，值得記錄】
//   舊版這裡寫的是 `HaplotypeCaller --BQSR ${recal_table}`。
//   但 GATK4 已經**移除**了 HaplotypeCaller 的 on-the-fly --BQSR 選項
//   （broadinstitute/gatk#6041）。這條路徑一執行就會直接報錯。
//   因為是「備援路徑」平常不會走到，所以這個 bug 潛伏了很久。
//   修正：改成標準的兩步 —— 先 ApplyBQSR 產生 recalibrated BAM，
//   再送進 HaplotypeCaller。這樣 CPU 備援的結果才會與 GPU 主線一致。
// ══════════════════════════════════════════════════════════════════════
process GATK_HAPLOTYPECALLER {
    tag "$meta.id"
    label 'process_high'

    publishDir "${params.out_dir}/${meta.id}/04_snv_indel", mode: 'copy'

    // INPUT:
    //   alignment_bundle - [BAM, BAI, recal.txt]
    //   fasta/fai/dict   - hg38 reference + index
    //   dbsnp            - dbSNP vcf + index (用於標註 rsID)
    input:
    tuple val(meta), path(bam), path(bai), path(recal_table)
    path fasta
    path fasta_fai
    path fasta_dict
    path dbsnp
    path dbsnp_idx

    // OUTPUT:
    //   vcf - HaplotypeCaller genotyped VCF（壓縮 + tabix index）
    output:
    tuple val(meta), path("*.haplotypecaller.vcf.gz"), path("*.haplotypecaller.vcf.gz.tbi"), emit: vcf

    script:
    // 1. 動態判斷：如果是 WES，加入 -L 與 Capture Kit BED 檔
    def interval_arg = params.seq_type == "WES" ? "-L ${params.wes_targets}" : ""

    // 2. 記憶體安全閥：總記憶體扣除 4GB，保留給作業系統與 C++ PairHMM 使用
    //    【為什麼要扣？】-Xmx 只限制 JVM heap，但 GATK 的 PairHMM 是 native C++（AVX 加速），
    //    它的記憶體在 heap 之外。若 -Xmx 設成跟 task.memory 一樣大，
    //    JVM + native 加起來就超過配額 → 被 cgroup OOM killer 砍（exit 137）。
    def avail_mem = task.memory ? (task.memory.toGiga() - 4) : 12

    """
# GATK4 已移除 HaplotypeCaller 的 on-the-fly --BQSR（broadinstitute/gatk#6041）。
    # 改為先 ApplyBQSR 產生 recalibrated BAM，再進 HaplotypeCaller，
    # 使 CPU 備援結果與 GPU 主線（Parabricks --in-recal-file）一致。
    gatk --java-options "-Xmx${avail_mem}g" ApplyBQSR \\
        -R ${fasta} \\
        -I ${bam} \\
        --bqsr-recal-file ${recal_table} \\
        -O ${meta.id}.recal.bam

    gatk --java-options "-Xmx${avail_mem}g" HaplotypeCaller \\
        -R ${fasta} \\
        -I ${meta.id}.recal.bam \\
        -O ${meta.id}.haplotypecaller.vcf.gz \\
        -D ${dbsnp} \\                                  # 標註 rsID
        -G StandardAnnotation \\
        -G StandardHCAnnotation \\
        ${interval_arg} \\
        --native-pair-hmm-threads ${task.cpus} \\       # PairHMM 的 AVX 平行度
        --max-reads-per-alignment-start 0               # 0 = 不做 downsampling
                                                        #   【為什麼？】預設會在高深度處隨機
                                                        #   丟棄 read（downsample）以加速，
                                                        #   但那會讓結果不可重現。臨床要可重現。

    rm -f ${meta.id}.recal.bam ${meta.id}.recal.bai     # recalibrated BAM 很大，用完即刪
    """
}

// ══════════════════════════════════════════════════════════════════════
// 【Process 4】GATK_VQSR_SNP
//
// Lane 2b: VQSR SNP（WGS only）
// 機器學習方法對 SNP 進行品質分層過濾
// WES 因變異數不足，跳過 VQSR，直接進 Ensemble
// 實測：RAM 9.4GB，CPU 123%（~1-2 cores）
// 記憶體由 config withName 個別設定為 12GB
//
// 【VQSR 原理，用一段話說】
//   硬性過濾（hard filter）是人工訂閾值：「QD < 2 就丟掉」。問題是每個閾值
//   都是拍腦袋決定的，而且各項指標之間的交互作用被忽略了。
//   VQSR 改用資料驅動：拿「已知為真」的變異（HapMap/Omni/1000G）當正例，
//   在多維註記空間（QD × MQ × FS × SOR × ...）擬合高斯混合模型，
//   算出每個變異的 VQSLOD 分數（屬於「真」分佈 vs「假」分佈的對數勝算比）。
//   最後依 tranche（敏感度分層）決定 FILTER 標記。
// ══════════════════════════════════════════════════════════════════════
process GATK_VQSR_SNP {
    tag "$meta.id"
    label 'process_medium'

    publishDir "${params.out_dir}/${meta.id}/04_snv_indel", mode: 'copy'

    // INPUT:
    //   vcf            - HaplotypeCaller 輸出的原始 VCF
    //   fasta/fai/dict - hg38 reference + index
    //   resources      - SNP 機器學習訓練所需的資料庫 (宣告於此以確保 Singularity 正確掛載)
    input:
    tuple val(meta), path(vcf), path(tbi)
    path fasta
    path fasta_fai
    path fasta_dict
    path hapmap
    path hapmap_idx
    path omni
    path omni_idx
    path known_snps
    path known_snps_idx
    path dbsnp
    path dbsnp_idx

    // OUTPUT:
    //   vcf      - SNP VQSR 過濾後的 VCF
    //   recal    - SNP recalibration model
    //   tranches - SNP sensitivity tranches
    output:
    tuple val(meta), path("*.vqsr_snp.vcf.gz"), path("*.vqsr_snp.vcf.gz.tbi"), emit: vcf
    path "*.snp.recal",    emit: recal      // 每個變異的 VQSLOD 分數（可追溯的中間產物）
    path "*.snp.tranches", emit: tranches   // 各敏感度層的 TP/FP 估計（評鑑可看的品質證據）

    script:
    def prefix = "${meta.id}"

    // 記憶體安全閥：保留 2GB 給系統與 Java 虛擬機外的開銷
    //   （VQSR 沒有 native PairHMM，所以只需要留 2GB，比 HaplotypeCaller 的 4GB 少）
    def avail_mem = task.memory ? (task.memory.toGiga() - 2) : 14

    """
    # 步驟一：建立 SNP 高斯混合模型 (VariantRecalibrator)
    gatk --java-options "-Xmx${avail_mem}g" VariantRecalibrator \
        -R ${fasta} \
        -V ${vcf} \
        -O ${prefix}.snp.recal \                     # 輸出：每個變異的 VQSLOD
        --tranches-file ${prefix}.snp.tranches \     # 輸出：敏感度分層表
        --trust-all-polymorphic \                    # 【重要】把 resource 中所有位點都當成
                                                     #   真正的多型性位點，不去檢查 AC/AN。
                                                     #   Broad 對單樣本 WGS 的官方建議：
                                                     #   不加這個，模型會因為 resource 中
                                                     #   「本樣本剛好是 hom-ref」的位點被誤導。

        # ---- tranche 分層：依敏感度切成幾層，每層報告 TP/FP 估計 ----
        -tranche 100.0 -tranche 99.9 -tranche 99.5 -tranche 99.0 -tranche 90.0 \

        # ---- 訓練特徵（-an = annotation）----
        -an QD \                # QualByDepth：品質除以深度（校正深度造成的品質膨脹）
        -an MQ \                # RMSMappingQuality：對位品質的均方根
        -an MQRankSum \         # ref/alt read 的 MAPQ 是否有系統性差異（有 = 可疑）
        -an ReadPosRankSum \    # 變異是否總是出現在 read 末端（是 = 可疑，通常是對位錯誤）
        -an FS \                # FisherStrand：strand bias 的 Fisher 精確檢定 p 值（Phred）
        -an SOR \               # StrandOddsRatio：另一種 strand bias 度量，對高深度較穩健
        -an DP \                # 【2026-07 新增】深度。Broad 對 **WGS** SNP 明確建議加入
                                #   （WES 則不建議，因為捕捉效率造成的深度變異不代表品質）。
                                #   這是評鑑後對齊 Broad 的其中一項修正。
        -mode SNP \
        --max-gaussians 8 \     # 高斯分量數。SNP 數量多（WGS 約 400 萬），可以用 8。
                                #   數量不足時 GATK 會報錯要求調低。

        # ---- 訓練資源。三個參數的意義：----
        #   known    = 是否用於「novel vs known」的分層報告（不影響模型訓練）
        #   training = 是否用來訓練「真」的高斯分佈
        #   truth    = 是否用來估計敏感度（tranche 的分母）
        #   prior    = 這個資源的可信度，Phred scale（15 = 錯誤率 10^-1.5 ≈ 3%）
        --resource:hapmap,known=false,training=true,truth=true,prior=15.0 ${hapmap} \
                                #   HapMap 3.3：最高品質的 truth set，prior 15（最可信）
        --resource:omni,known=false,training=true,truth=false,prior=12.0 ${omni} \
                                #   1000G Omni 2.5 晶片：高品質但非 truth
        --resource:1000G,known=false,training=true,truth=false,prior=10.0 ${known_snps} \
                                #   1000G phase1 高信心 SNP：擴充訓練集
        --resource:dbsnp,known=true,training=false,truth=false,prior=2.0 ${dbsnp}
                                #   dbSNP：只用來標記 known/novel，prior 只有 2
                                #   （dbSNP 品質參差，不適合當訓練集）

    # 步驟二：套用模型並執行過濾 (ApplyVQSR)
    gatk --java-options "-Xmx${avail_mem}g" ApplyVQSR \\
        -R ${fasta} \\
        -V ${vcf} \\
        -O ${prefix}.vqsr_snp.vcf.gz \\
        --recal-file ${prefix}.snp.recal \\
        --tranches-file ${prefix}.snp.tranches \\
        --truth-sensitivity-filter-level 99.5 \\   # 【關鍵閾值】保留能抓到 99.5% truth set
                                                   #   變異的那個 VQSLOD 門檻以上的變異。
                                                   #   剩下 0.5% 標記為 FILTER。
                                                   #   Broad 對 germline WGS SNP 的建議值。
                                                   #   調高 → 更敏感但更多假陽性；調低則相反。
        -mode SNP
    """
}

// ══════════════════════════════════════════════════════════════════════
// 【Process 5】GATK_VQSR_INDEL
//
// Lane 2b: VQSR INDEL（WGS only）
// SNP VQSR 完成後，對同一 VCF 再做 INDEL VQSR
// 實測：RAM 6.5GB，CPU 132%（~1-2 cores）
// 記憶體由 config withName 個別設定為 10GB
//
// 【與 SNP 版的三個關鍵差異，都是有原因的】
//   1. 少了 -an MQ 與 -an DP
//   2. max-gaussians 從 8 降到 4
//   3. filter level 從 99.5 降到 99.0
//   理由見下方各行註解。
// ══════════════════════════════════════════════════════════════════════
process GATK_VQSR_INDEL {
    tag "$meta.id"
    label 'process_medium'

    publishDir "${params.out_dir}/${meta.id}/04_snv_indel", mode: 'copy'

    // INPUT:
    //   vcf            - VQSR_SNP 輸出的 VCF（已完成 SNP 過濾）
    //   fasta/fai/dict - hg38 reference + index
    //   resources      - 機器學習訓練所需的資料庫 (必須宣告在這裡才能掛載進 Container)
    input:
    tuple val(meta), path(vcf), path(tbi)
    path fasta
    path fasta_fai
    path fasta_dict
    path mills
    path mills_idx
    path axiom
    path axiom_idx
    path dbsnp
    path dbsnp_idx

    // OUTPUT:
    //   vcf - SNP + INDEL VQSR 雙重過濾後的最終 VCF
    output:
    tuple val(meta), path("*.vqsr_indel.vcf.gz"), path("*.vqsr_indel.vcf.gz.tbi"), emit: vcf

    script:
    def prefix = "${meta.id}"

    // 記憶體安全閥：保留 2GB 給系統與 Java 虛擬機外的開銷
    def avail_mem = task.memory ? (task.memory.toGiga() - 2) : 10

    """
    # 步驟一：建立 INDEL 高斯混合模型 (VariantRecalibrator)
    gatk --java-options "-Xmx${avail_mem}g" VariantRecalibrator \
        -R ${fasta} \
        -V ${vcf} \
        -O ${prefix}.indel.recal \
        --tranches-file ${prefix}.indel.tranches \
        --trust-all-polymorphic \
        -tranche 100.0 -tranche 99.9 -tranche 99.0 -tranche 90.0 \   # 比 SNP 少一層（沒有 99.5）
        -an QD -an MQRankSum -an ReadPosRankSum -an FS -an SOR \
        #   【為什麼沒有 -an MQ？】indel 附近的 read 對位品質天生就低
        #   （因為 indel 本身就會造成 mismatch），MQ 對 indel 幾乎沒有鑑別力，
        #   放進去只會讓模型學到「所有 indel 都可疑」。Broad 官方也不建議。
        #   【為什麼沒有 -an DP？】同上，Broad 只對 WGS **SNP** 建議加 DP。
        -mode INDEL \
        --max-gaussians 4 \     # 【為什麼從 8 降到 4？】indel 數量遠少於 SNP
                                #   （WGS 約 80–100 萬 vs 400 萬），
                                #   高斯分量太多會過擬合，GATK 也會直接報錯拒跑。
                                #   4 是 Broad 對 indel 的標準建議值。

        --resource:mills,known=false,training=true,truth=true,prior=12.0 ${mills} \
                                #   Mills gold standard indels：indel 界的 truth set
                                #   prior 12（比 SNP 的 HapMap 15 低，因為 indel 本身較難確認）
        --resource:axiomPoly,known=false,training=true,truth=false,prior=10.0 ${axiom} \
                                #   Axiom Exome Plus：擴充 indel 訓練集
        --resource:dbsnp,known=true,training=false,truth=false,prior=2.0 ${dbsnp}

    # 步驟二：套用模型並執行過濾 (ApplyVQSR)
    gatk --java-options "-Xmx${avail_mem}g" ApplyVQSR \
        -R ${fasta} \
        -V ${vcf} \
        -O ${prefix}.vqsr_indel.vcf.gz \
        --recal-file ${prefix}.indel.recal \
        --tranches-file ${prefix}.indel.tranches \
        --truth-sensitivity-filter-level 99.0 \   # 【為什麼比 SNP 的 99.5 低？】
                                                  #   indel 的 truth set 品質較差、
                                                  #   模型鑑別力較弱，取 99.5 會把太多
                                                  #   真 indel 的 FILTER 標成 PASS（過寬）。
                                                  #   99.0 是 Broad 對 indel 的建議值。
        -mode INDEL
    """
}
```

## 6.4 ⚠️ 為什麼 HaplotypeCaller 要「等」DeepVariant

Nextflow 的排程是**資料驅動**的：只要 input channel 有元素，task 就會被排入佇列。
DV 和 HC 兩個 process 都只吃 `bam_ch` → 它們會**同時**被排程。

在單卡機器（DGM）上，兩個 Parabricks process 同時佔用同一張 16 GB VRAM 的卡
→ **必定 CUDA OOM**。

解法是在 `CALL_SNV` 裡人工建立資料相依：

```groovy
ch_bam_after_dv = bam_ch
    .join(ch_dv_vcf.map { meta, vcf, tbi -> [meta, meta.id] })
    .map { meta, bam, bai, recal, dummy -> [meta, bam, bai, recal] }
```

`join` 要兩邊都有同一個 key 才會發射。DV 沒完成 → `ch_dv_vcf` 是空的 →
`join` 不發射 → HC 不會開始。DV 一完成，join 立刻發射原本的 BAM tuple，HC 才開跑。

第二個元素 map 成 `meta.id`（一個字串）而不是整個 VCF，是為了避免
Nextflow 為了 join 而把 VCF 檔案物件搬來搬去。

## 6.5 評鑑速查：SNV/indel 相關問答

| 問題 | 答案 |
|------|------|
| 「為什麼用兩個 caller？」 | 錯誤模式不相關；雙 caller 一致 = 高信心，單 caller = 三級標記 `CALLERS` 供判讀 |
| 「WES 為什麼不做 VQSR？」 | 變異數不足（3–5 萬 vs WGS 400 萬），高斯混合模型訓不起來；GATK 官方建議 |
| 「VQSR 的閾值怎麼定的？」 | SNP 99.5 / INDEL 99.0，皆為 Broad germline 官方建議值，非自訂 |
| 「為什麼 SNP 有 `-an DP` 而 INDEL 沒有？」 | Broad 只對 WGS SNP 建議；此為 2026-07 評鑑後對齊 Broad 的修正之一 |
| 「DeepVariant 有做 BQSR 嗎？」 | 沒有，Google 官方建議不做；HC 則透過 `--in-recal-file` 即時套用 |
| 「結果可重現嗎？」 | 可以：bwa `-K` 固定批次、HC `--max-reads-per-alignment-start 0` 關閉 downsampling |
| 「中間產物有保留嗎？」 | `*.snp.recal` / `*.snp.tranches` / `*.indel.*` 全部發布在 `04_snv_indel/` |
